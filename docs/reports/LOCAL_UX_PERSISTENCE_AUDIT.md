# 本地视觉巡检：交互与会话恢复

- 巡检日期：2026-09-03
- 范围：本机开发服务的匿名临时会话；不代表公网生产环境结果。
- 方法：通过浏览器实际上传仓库内 README、生成路线、进入阶段精读、打开检查器、刷新和触发阶段结束决策，并以页面截图核对可见状态。DOM 定位只用于执行已可见控件，并非结论依据。
- 巡检材料：项目 README，生成 4 个阅读阶段；未使用用户的私有资料。

## 结论

当前产品的已提交业务状态在同一个 Next.js 进程、同一个匿名 Cookie 内可以在刷新后恢复；路线、当前阶段和已生成的精读消息仍可见。这个结果不能证明其适合公网交付：会话数据仍只存在单个 Node 进程的 Map 中，服务重启、冷启动、发布替换或多实例负载均衡都会使它不可恢复。

同时，刷新后丢失的右侧栏开合、选中标签、未提交追问、滚动位置和决策弹窗属于客户端临时交互状态。Redis 解决的是服务器业务状态的跨进程恢复，**不会自动修复这些 UI 状态或不清晰的导航语义**。

## Redis 之外仍需保留的边界

1. Redis 不能赋予返回正确的业务语义，也不能让多个页面自然恢复；路由、禁用态和取消动作仍是界面设计问题。
2. Redis 不能使未提交表单、滚动位置或临时动画自然持久；这些信息应按需留在浏览器端，避免把输入过程写成服务端用户数据。
3. Redis 不是长期笔记库、账号系统或历史会话产品。匿名临时会话过期后仍应删除；需要跨设备、长期检索和审计时再引入身份与持久数据库。
4. 视觉巡检只覆盖文本型 README、小规模路线和单标签页。RFC/MyBatis 长文、模型异常、两标签页并发、Redis 故障及公网移动网络仍要在 P6.0/P6 验收。

## 对后续交付的含义

Redis 会将刷新后偶然还在的本地体验提升为在部署重启和单次实例切换后仍可恢复的两小时匿名会话，是公网 Demo 的必要底座之一；它不是当前 UX 问题的替代修复。推荐顺序为：先落地 P6.0 的 Redis 会话存储与恢复验收，再处理上述 UI 交互项，最后部署并做公网回归。
