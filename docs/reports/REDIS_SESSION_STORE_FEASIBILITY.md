# Redis 临时会话存储：可行性分析与执行指导

- 版本：v0.2 / P6.0 讨论基线
- 日期：2026-09-03
- 决策状态：**建议采纳，待用户确认 Redis 服务形态与部署环境后实施**。
- 本文不授权创建云服务、安装客户端或迁移代码。

## 1. 要解决的业务问题

Lumen 的公开交付不是一次录屏，而是让面试官在公网浏览器中完成导入、画像、路线、阶段精读和笔记下载。当前匿名 Cookie 只保存随机会话 ID；来源分块、画像、路线、阶段消息和笔记存在 Next.js 进程内的 SessionStore 中。

这在单台本地开发服务器中够用，但服务重启、版本发布、冷启动或多实例路由都会失去内容。用户提出用 Redis 作为 JSON 临时缓存，正好匹配匿名、短期、无需关系查询、以整个会话读取和更新为主的 v0.2 边界。

目标是让**已提交的业务状态**在 Redis TTL 内跨应用进程恢复；不扩大为登录、长期历史、跨设备资料库或完整数据库产品。

## 2. 方案比较与结论

| 方案 | 交付稳定性 | 额外工程量 | 适合性 | 结论 |
| --- | --- | --- | --- | --- |
| 继续进程内 Map | 仅单进程存活期间可用；重启或多实例丢失 | 无 | 仅本地原型 | 不适合公网体验。 |
| Redis 单会话 JSON 加 TTL | 跨进程、跨实例恢复；到期自动删除 | 中等，可控 | 匿名两小时精读会话 | **推荐 P6.0 采用。** |
| Redis 拆分多 Hash 或 RedisJSON 文档模型 | 可局部更新，但需要事务、索引和更多迁移逻辑 | 中高 | 高并发或复杂查询 | 当前过度设计；不依赖 RedisJSON 模块。 |
| MongoDB | 文档模型自然、可长期保存 | 中高：账号、索引、备份、权限设计随之出现 | 将来多文档历史 | 当前不需要。 |
| PostgreSQL/MySQL 加 Redis | 可审计、关系查询和长期历史能力强 | 高：表设计、迁移、连接池、数据生命周期 | 正式产品 | 作为 v0.4 以后演进，不是本次面试 Demo 的第一步。 |

因此采纳“**Redis 是匿名临时业务会话的权威存储；Cookie 只携带不透明会话 ID；TTL 到期后删除**”这一技术取舍。它不是关系数据库的替代品，而是对当前明确数据生命周期的合适最小解。

## 3. 推荐数据模型

### 3.1 键与 TTL

```text
tdr:session:v1:{sessionId}      -> JSON.stringify(SessionState)，TTL 为 2h（滑动）
tdr:session-lock:v1:{sessionId} -> 可选短锁或令牌，用于并发写保护
```

- 使用命名空间、实体名和版本号；键中绝不出现文件名、URL、用户输入或文档正文。
- Cookie 继续只放随机 UUID，保持 HttpOnly、SameSite=Lax，生产环境启用 Secure；绝不将整个 JSON 会话放入 Cookie 或浏览器本地存储。
- 每次可信的读取触碰或成功写入都刷新键 TTL，维持现有 2 小时滑动会话约定。TTL 是删除策略，不是备份机制。
- 首版使用标准 Redis GET / SET 和 JSON.stringify；不要假设托管服务提供 RedisJSON module。

### 3.2 单个 JSON 的理由

当前 SessionState 是紧密嵌套的工作单元：source（元数据与分块）、profile、plan（含阶段与消息）、notes、requestLog 和 streamingStageId。现有业务逻辑以读取会话对象、校验和修改、形成响应为主，而不是对单个笔记做全局查询。

首版将一个会话存为一个 Redis value，减少键清理、跨键事务、部分更新失败和测试面。未来若发生以下任一情况，再拆分：单会话超过 provider 的单值限制、消息或笔记需要独立分页、需要跨会话搜索，或需要长期保存。

### 3.3 大小边界

- 现有入口允许单文件最大 10 MB，并对索引文本限制为 500,000 字符；解析分块需要保留在会话中以支撑检索和引用。
- 单 value 不能无限制增长。实施时应记录安全的序列化字节数，并先设 **1 MiB 告警、2 MiB 拒绝写入或降级提示** 的初始保护值；最终阈值必须以实际 provider 的最大 value、内存配额和 MyBatis/RFC 压测结果校准。
- 不应为了全部恢复把原始二进制 PDF 写入 Redis。存已解析、已受上限约束的文本分块和元数据即可；原文件本来就不是当前读取链路的必需输入。
- 超限时返回明确可重试错误，保留用户已下载笔记的出口，不静默截断引用来源。

## 4. 一致性、流式与故障语义

Redis 不会自动消除并发问题。当前内存对象可以被原地修改；迁移后若两个请求分别 GET 同一 JSON 后各自 SET，后写入者会覆盖前者。

### 必须保留的状态约定

1. streamingStageId 是业务锁：开始 SSE 前必须持久化写入；流式完成后，连同最终助手消息、阶段状态和清锁一次提交；异常或客户端断开必须释放锁。
2. 同一会话的开始阶段、追问、结束阶段、笔记接受或跳过、替换来源都是写操作，必须带版本检查或短锁。
3. 优先方案：在 SessionState 增加 version，用 Redis WATCH / MULTI 或 Lua compare-and-set 实现“读取版本、修改、仅当版本一致时写入加 EX”。冲突时有限重试，再返回“会话在另一标签页更新，请刷新”。
4. 若首版采用短锁，锁必须有很短 TTL 且仅包围会话变更；不能在模型流式生成全程持有长锁。流式期间应靠持久化的 streamingStageId 拒绝第二次阶段动作。
5. Redis 不可用时，不能悄悄退回新的进程内 Map，否则同一用户会看到随机丢失。应返回可重试的“临时会话服务不可用”，保留已提交数据并触发监控。

## 5. 运行时和供应商选择

| 目标部署形态 | 推荐客户端 | 说明 |
| --- | --- | --- |
| Render 等常驻 Node 服务，Redis 与应用同区域且支持 TCP/TLS | redis（node-redis） | 标准协议、直接，适合长驻连接；Route Handlers 使用 Node runtime。 |
| Vercel/Edge 或连接生命周期短的 serverless | @upstash/redis | HTTP/REST 更适合 serverless；需核对套餐、区域和请求成本。 |

在用户尚未确定托管平台前不安装任何客户端。无论选择哪种服务，都必须确认：应用与 Redis 同区域、TLS、认证、闲置策略、连接或请求上限、单 key 最大值、内存额度、备份或日志政策和关闭资源方式。

安全底线：Redis 仅允许服务端私网或 TLS 认证连接，禁止向公网暴露端口；REDIS_URL 仅放在服务端环境变量；错误日志不得打印连接 URL、密码、会话 JSON、文档正文或模型输入。页面要说明内容最长临时保存 2 小时。

## 6. 建议实施分段（确认后）

### P6.0a：存储边界抽象

- 定义 SessionRepository 接口（创建、读取/触碰、原子更新、删除或失效、大小校验）。
- 业务层继续面向 SessionState 和现有服务函数，不让 Redis client 扩散到 route/service。
- 先让现有内存实现成为该接口的测试替身，保证 P2 至 P5 行为不变。

**退出标准：** 单元测试不依赖真实 Redis；现有流程保持通过。

### P6.0b：Redis 适配器与本地契约

- 新增 Redis adapter、REDIS_URL 配置说明和不含密钥的 .env.example。
- 开发环境可提供独立、最小的 Redis Compose 服务；不把生产密钥、原始文件或数据库卷提交到仓库。
- 写入时执行序列化大小保护、TTL 续期与版本/CAS。

**退出标准：** 新建、上传、路线、消息、笔记的每次成功写入均在 Redis 内以会话键和剩余 TTL 可验证。

### P6.0c：流式和冲突回归

- 改造 prepareStageAction 和 executePreparedStage 的“加流式锁、提交消息或清锁”边界。
- 增加两标签页双提交、SSE 中断、模型失败、Redis 短暂不可用和笔记重复接受测试。

**退出标准：** 不出现重复助手消息、卡死 streamingStageId 或后写覆盖笔记。

### P6.0d：恢复与部署验收

- 完整执行导入至笔记下载；刷新、重新进入 reading 页面、重启应用后均恢复已提交数据。
- 验证 TTL 到期返回明确会话过期状态，而非空白页；验证两实例或等价的不同应用进程读取同一 Redis 情形。
- 再配置部署平台 secret、健康检查和 Redis 不可用告警。

**退出标准：** P6 的公网主流程五次至少四次成功，且会话服务故障有可解释的失败状态。

## 7. 明确不由 Redis 负责的事项

- 未提交 textarea 草稿、弹窗开合、右侧标签选择和滚动位置：先视为客户端临时状态；需要恢复时用受限的 sessionStorage 或 URL 状态单独设计。
- 登录、历史列表、多会话切换、跨设备所有权和长期保留：需要身份模型与持久数据库，不随本次迁移自动获得。
- 跨文档 RAG、联网、AI 助教、多 Agent 和外部工具：仍按 v0.3 以后范围另行评审。
- 文档隐私合规：Redis TTL 降低保留时间，但不替代供应商数据处理评估、访问控制和日志脱敏。

## 8. 需要用户确认的外部条件

1. 公网部署目标（优先 Render 还是其他平台）与预期运行期限。
2. 是否已有可用 Redis 实例；若没有，允许使用哪家托管服务、月度预算与账号创建权限。
3. 会话临时保存仍为 2 小时，还是需要不同期限；期限改变会影响成本与隐私说明。
4. P6 是否需要访问口令，以限制公开 API 消耗和匿名上传风险。

在这四项确认前，本文作为可实施设计基线，代码仍保持当前内存实现。
