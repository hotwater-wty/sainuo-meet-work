# 体验审查与 AI 助教评估报告

- 版本：`v0.2` 讨论基线
- 日期：2026-09-02
- 状态：设计审查，暂不实现本报告提出的新功能

## 1. 结论摘要

当前主流程的后端闭环已经成立，但页面仍更像“生成结果页面”，不像连续的精读工作区。首轮体验最需要解决的是结果可读性、对话位置和过程可见性，而不是增加更多模型能力。

本轮建议按以下顺序处理：

1. 完整回答结束后统一渲染 Markdown，并把引用标记转换为来源入口。
2. 将阶段精读移入可收起的右侧对话抽屉，保留路线和文档地图作为主内容。
3. 复验导入到笔记导出的完整路径，再进行公网部署。
4. 将“AI 助教”作为 `v0.3` 的窄范围实验，不阻塞当前 `v0.2` 交付。

## 2. 体验问题审查

### 2.1 已观察到的问题

- 选择文件和完成导入此前没有明显的状态区别，用户不知道下一步要做什么，也看不到完整路径。
- 页面原先的 Next.js `N` 开发工具使用英文抽屉，容易被误认为产品设置；这不是产品功能，已在 `next.config.ts` 中关闭，待复验。
- 精读内容直接以普通段落显示。截图中可见 `###`、`**粗体**`、列表符号和 `[S1]`，它们失去了 Markdown 的层级、强调、代码和引用交互。
- 阶段内容、检查问题、路线卡片和文档地图在同一纵向页面竞争空间。用户需要滚动很长距离才能回到输入框或确认阶段。
- 阶段状态与对话状态的边界不够明显。用户可能把“正在生成”误认为“已保存”，或不清楚完成后下一步是回答问题还是确认笔记。

### 2.2 影响和优先级

`UX-001`、`UX-002` 属于已处理的首轮阻塞问题，等待用户复验。`UX-007`（Markdown 可读性）和 `UX-008`（对话抽屉）是高优先级，因为它们直接影响 Demo 是否形成“导入后可持续学习”的闭环。`UX-009` 至 `UX-012` 是随重构必须补齐的状态、引用和语言一致性问题，详见 `docs/UX_ISSUES.md`。

## 3. Markdown 渲染方案

### 方案 A：生成完成后统一渲染（当前推荐）

流式期间显示安全的临时纯文本；服务端确认响应完整后，客户端把内容交给 Markdown 解析器并作为正式消息渲染。

优点：

- 未闭合的代码围栏、列表、表格不会持续改变页面结构，布局更稳定。
- 可以在完整文本上一次性解析 `[S1]` 等引用，并验证其是否属于本轮真实来源。
- 更容易禁止原生 HTML，降低不可信内容被当作页面执行的风险。
- 改造范围小，适合当前面试交付和现有“流式临时状态、完成后原子提交”的后端约定。

代价：

- 用户在生成过程中看到的是纯文本，视觉反馈不如实时渲染丰富。
- 长回答需要等待结束后才形成最终排版。

### 方案 B：边生成边增量渲染

每收到一批 token 就重新解析 Markdown 并更新消息。

优点是反馈更接近网页版 AI 对话工具，长回答的首屏可更早形成层级；代价是需要处理未闭合语法、代码块增长、自动滚动、引用按钮反复重建和最终文本闪烁。若模型中断，还要区分可展示的临时内容和可保存的正式内容。

### 决策

`v0.2` 采用方案 A。建议技术实现为 `react-markdown` + `remark-gfm`，禁止原生 HTML，统一标题、列表、代码块、表格和引用样式。流式完成后再切换到正式渲染状态；后续若首屏等待成为主要抱怨，再单独评估增量渲染，而不在当前重构中同时引入。

## 4. 侧边精读助手设计

### 布局和交互

- 桌面端主区域展示文档地图、路线和当前阅读上下文；右侧抽屉宽度建议约 400–480px，可展开/收起。
- 抽屉顶部显示阶段编号、标题、状态和关闭按钮；中部为消息与引用；底部固定输入框、检查问题和阶段操作。
- 路线卡片的“开始阶段”操作自动打开抽屉并定位到对应阶段。关闭抽屉只改变可见性，不清除 `selectedStageId`、消息、草稿或阶段状态。
- 移动端抽屉使用接近全宽的侧滑面板，保留明确的关闭入口；输入区固定在面板底部，避免长页面底部操作。

### 实现边界

现有 `selectedStageId`、`streamingText`、`runStageAction` 和 `StageWorkspace` 已覆盖阶段状态机，数据层无需重写。主要工作是拆分内联布局、补充打开/关闭状态、调整响应式样式和完善状态提示，属于中等难度的 UI 重构。

## 5. AI 助教需求评估

### 产品职责

AI 助教应是“基于当前文档的跨阶段问答入口”，与“推进单个阶段的精读助手”分工：前者回答随时提出的全局问题，后者负责讲解、检查和完成阶段。两者应使用独立的消息列表，避免普通问答改变阶段状态。

### 推荐上下文策略

每次提问按需组装上下文，而不是把所有材料全部发送给模型：

- 当前问题作为主查询。
- 从文档分块中召回 Top-K 原文片段。
- 仅加入与问题相关的文档地图字段。
- 只从 `accepted` 阶段笔记中按相关性筛选；`pending` 草稿不作为默认事实来源。
- 当前阶段内容只能作为可选增强，不默认拼接全部阶段历史。
- 服务端设置字符/token 上限，继续只允许模型使用真实来源 ID。

### 难度、成本和风险

基础版（单文档、Top-K 原文 + 相关已确认笔记、独立问答接口）为中等难度，预计约半至一个开发日。完整版本还需要独立聊天历史、上下文选择器、SSE、抽屉 UI 和更多异常测试，属于中高难度。

主要风险包括上下文重复导致费用和延迟上升、用户笔记与原文事实混淆、引用 ID 合法但语义支持不足，以及两个入口让用户不清楚该向谁提问。回答证据不足时必须明确提示，不能用模型参数或未提供的网页内容补齐。

### 是否纳入当前计划

建议纳入长期产品方向，但不插入 `v0.2` 的 P2–P6 主交付链路。若面试演示时间有余量，可在部署稳定后做 `v0.3 / P6-AI 助教实验`：只支持当前文档，不联网、不跨文档、不做长期记忆、不调用外部工具。若时间不足，保留本报告和接口草案即可，不影响当前 Demo 的完整性。

## 6. 验收门槛与后续顺序

体验稳定化至少应满足：完整回答的 Markdown 层级可读；引用可点击并能定位；抽屉开关不丢状态；桌面和 390px 移动视口无遮挡；生成中断不写入正式消息或笔记；导入、路线、阶段、笔记和下载路径可被首次用户理解。

滚动顺序锁定为：Markdown 渲染 → 侧边抽屉 → 主流程复验 → P6 公网质量与安全 → P7 面试材料。AI 助教排在公网 Demo 稳定之后。
