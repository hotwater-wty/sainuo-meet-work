# Codex 式工作区、会话与登录存储方案评估

- 日期：2026-09-02
- 版本：`v0.2` 体验稳定化决策报告
- 状态：建议已形成，暂不实施数据库与登录

## 1. 结论

可以借鉴 Codex 的工作区结构，但不应复制它背后的账号、项目、历史任务和云同步能力。当前面试 Demo 的核心评价点仍是“导入技术文档后完成可信精读”，工作区框架只应降低操作成本，不能成为新的产品主线。

推荐决策如下：

1. 保留可收起侧栏、当前阅读、来源信息和新建入口，但把“新建会话”改称“新建精读”，使名称符合单文档产品语义。
2. `v0.2` 继续使用单实例进程内会话和 2 小时 TTL，不引入数据库、注册或登录。
3. 不实现半成品历史列表。当前按钮只创建新内存会话，旧会话无法找回，不能包装成历史能力；未实现前应隐藏“历史会话”入口，而不是保留可点击占位。
4. Next.js 开发工具继续关闭。若需要开发诊断，后续实现项目自有的中文调试面板，并在公网环境默认关闭。
5. 设置入口只有在至少包含一项真实可生效的设置后再展示；登录入口等到持久化和多用户范围正式立项后再出现。
6. 数据库 + 登录作为未来 `v0.4` 能力评估，不进入 P5.5、P6 上线或 `v0.3` AI 助教实验。

## 2. 当前能力与容易产生的误解

当前系统以 `tdr_session` HttpOnly Cookie 标识一个匿名会话，服务端 `SessionStore` 在进程内保存来源块、阅读画像、路线、阶段消息和笔记。刷新页面可恢复；2 小时无活动后过期；服务重启或切换实例后允许丢失。

现有“新建会话”会创建新的内存对象并覆盖浏览器 Cookie。旧对象在 TTL 内仍占用服务器内存，但浏览器没有会话索引，也没有切回旧对象的入口。因此当前功能是“开始一份新的临时精读”，不是多会话历史。

这一区别影响演示表述：

- 可以承诺：新建、刷新恢复、当前文档临时保存、导出成果。
- 不能承诺：历史对话、跨设备同步、登录后找回、多用户数据隔离、服务重启恢复。

## 3. 是否需要新建与历史会话

### 新建精读：建议保留

新建能力对 Demo 有实际价值：评审者可以在不清理 Cookie 或重启服务的情况下重新走一遍主流程，也能从 MyBatis 切换到 RFC。它应执行以下业务约定：

- 有当前文档时先确认，并提示未导出的进度不会出现在历史列表中。
- 创建新的匿名内存会话，旧会话按 TTL 自然清理。
- 跳转到 `/home` 导入入口，不自动调用模型。
- 文案使用“新建精读”，避免让用户期待通用聊天和永久历史。

### 历史会话：当前不建议实现

历史列表并非主闭环所需，且会引入会话所有权、列表排序、标题生成、切换、删除、过期提示和服务重启失效等新问题。在原题 4–6 小时、1–2 天的交付语境下，它对评审价值低于 Markdown 渲染、精读抽屉、引用可信度和公网稳定性。

如果只用内存实现历史，需要额外增加匿名工作区 ID、工作区与多个会话的所有权校验、列表/切换 API，并明确“仅本浏览器、仅两小时、服务重启丢失”。预计需要 0.5–1 个开发日，仍不能形成可信的长期历史，因此不推荐在当前阶段投入。

## 4. 三种存储方案比较

| 方案 | 能力 | 实现成本 | 主要风险 | 当前建议 |
| --- | --- | --- | --- | --- |
| 单活动内存会话 | 刷新恢复、新建精读、TTL 清理 | 已完成 | 重启/多实例丢失，不能找回旧会话 | `v0.2` 采用 |
| 匿名内存多会话 | 本浏览器短期列表与切换 | 中，约 0.5–1 日 | 用户误以为已持久化；所有权和过期状态变复杂 | 不做 |
| 数据库 + 登录 | 长期历史、跨设备、多用户隔离 | 高，约 2–4 日以上 | 认证、授权、迁移、隐私、删除、部署和文件生命周期全面扩张 | 未来 `v0.4` |

不建议为了“先有数据库”而引入 SQLite。当前计划使用托管平台，临时或多实例文件系统不保证持久化；若未来正式进入账号阶段，应直接选托管 PostgreSQL，并结合部署平台确定认证服务和对象存储。

## 5. 为什么数据库不能单独解决问题

把会话写入数据库只能解决“进程重启后数据还在”，不能自动解决“谁能读取哪条会话”。一旦页面提供历史列表，就必须建立稳定的用户或匿名主体，并在每个查询、切换、下载和删除接口校验所有权。

完整账号化至少涉及：

- 用户、登录会话和身份回调。
- 阅读会话、文档、来源块、阶段消息、笔记的归属关系。
- 文档正文或原文件的保存位置、加密、大小限制和删除策略。
- 多实例一致性、数据库迁移、备份和连接池。
- 隐私披露、用户主动删除、账号退出和越权访问测试。
- 公开 Demo 的注册滥用、验证码或 OAuth 配置及运维成本。

这些工作会把项目从“单文档 AI 应用 Demo”转变为“多用户 SaaS 基础设施项目”，不符合当前稳定交付优先级。

## 6. 设置与开发者工具建议

### 产品设置

不建议为了界面完整而展示无效设置。后续可先做一个轻量设置抽屉，而不是独立复杂页面，只收纳真实生效且不改变安全边界的项目：

- 默认界面主题：浅色或跟随系统。
- 默认侧栏状态：展开或收起。
- 回答展示偏好：生成中纯文本、完成后 Markdown（当前策略只读展示）。
- 临时数据说明：2 小时 TTL、服务重启丢失、清空当前精读。

模型地址、API Key、系统提示词、检索阈值和 token 上限属于服务端运维配置，不应让公网用户在设置中修改。

### 中文开发诊断面板

Next.js 自带开发工具不属于产品 UI，难以可靠翻译，也会暴露框架细节；应继续通过 `devIndicators: false` 隐藏。确有开发和演示诊断需求时，可实现自有面板：

- 环境变量控制，例如 `ENABLE_DEBUG_PANEL=true`；生产默认关闭。
- 中文展示模型名称、thinking 状态、会话剩余时间、来源块数量、最近一次模型延迟和引用数量。
- 允许复制脱敏诊断信息。
- 不展示 API Key、完整提示词、完整文档正文、Cookie 或内部堆栈。

这个面板预计 0.25–0.5 日，只有在 P6 调试或面试材料需要可观测证据时才值得实现。

## 7. Codex 式交互应借鉴什么

建议借鉴的是信息架构，而不是功能数量：

- 左侧栏负责开始任务、定位当前阅读和展示来源。
- 主区域负责文档地图与路线。
- 右侧抽屉负责阶段精读和后续 AI 助教。
- 顶栏负责返回、产品首页和临时会话状态。

不应为了视觉相似而提前加入项目分组、无限历史、账号中心、插件、通知或云同步。对当前产品而言，“新对话”也应翻译成领域动作“新建精读”。

## 8. 推荐执行顺序

### 当前 `v0.2 / P5.5`

1. 完成 Markdown 渲染、右侧精读抽屉和主流程复验。
2. 将“新建会话”改为“新建精读”，隐藏未实现的历史与登录入口。
3. 设置入口暂时隐藏；若时间充足，只实现轻量、真实生效的设置抽屉。

### `P6` 公网部署

继续使用单实例长驻 Node 服务、内存 TTL、限流和模型预算。页面清楚披露临时保存边界；演示前准备预置材料和可重复的新建精读入口。必要时加入生产默认关闭的中文诊断面板。

### 后续版本

- `v0.3`：单文档 AI 助教实验，继续复用当前匿名会话。
- `v0.4`：只有在明确需要长期历史、跨设备或真实多用户时，再整体设计 PostgreSQL、认证、授权和文件生命周期。

## 9. 决策门槛

只有同时满足以下条件，才进入数据库与登录阶段：

1. 产品目标明确要求用户下次回来继续阅读，或需要跨设备访问。
2. 已选定部署平台、托管数据库、认证方式和费用上限。
3. 已定义文档保留期限、删除能力、敏感资料策略和所有权校验。
4. 当前单文档精读 Demo 已稳定上线，新增基础设施不会影响面试交付。

在这些条件满足前，保持内存会话不是技术欠账，而是与当前交付目标一致的范围控制。
